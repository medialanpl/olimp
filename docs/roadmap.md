# Roadmap

Each stage ends with a checkable criterion. The decision on opening the code is part of stage 10.

OLIMP is one monolith on one machine: one process serves the API and MCP and runs the
worker and the scheduler. A repository is the unit of knowledge and access: its notes, integrations
and tasks belong to it, so several repositories are several separate areas. Outside systems connect
through MCP, as integrations an agent step chooses. The web panel comes before the move of medialan.

| Stage | Scope | Done when |
|---|---|---|
| 0 | Skeleton: task from Git → Claude → PR, REST API, MCP, SQLite | a task created through the API or MCP on a real GitHub repository ends with a PR |
| 1 | Second runner (Codex) and the runner interface | a task can choose `agent: "codex"` through the API or MCP and the pipeline test with a fake `codex` ends with a PR; a live Codex run waits for a user with Codex (maintainer's decision: adding the runner is enough) |
| 2 | Skills and automations with a schedule | a scheduled automation runs a task with a chosen skill: skills repositories and automations are managed through the API and MCP, and the pipeline test (`test/flow.test.ts`) takes an automation due in the current minute through the scheduler to a PR whose agent was told to read the skill copied into the worktree and whose commit leaves the skill out; a Codex task gets the skill the same way |
| 3 | Workflows as graphs (n8n-like) | a workflow of at least agent, condition and PR steps runs end to end |
| 4 | User memory linked to tasks (Jarvis-like) | a task reads notes from earlier tasks of the same user and writes new ones |
| 5 | MCP integrations of a repository and GitHub issues as a task source | an agent step of a workflow uses a tool from its repository's MCP server and the run ends with a PR; an issue labelled for OLIMP creates a task whose PR closes it |
| 6 | Second database (MySQL, as in Corivo) and the database interface; first (6a) an asynchronous store and numbered migrations on SQLite, then (6b) MySQL | the test suite passes on SQLite and MySQL |
| 7 | Repository memory structure: sections, hubs and sources in the notes system (Jarvis-like) | a task reads a hub and a section of its repository's memory and writes into a section with its source |
| 8 | Sandbox and multiple users; first (8a) the agent's allowed environment and the repository's allowed commands, without containers (maintainer's decision), then (8b) users in shared repositories, each with their own agent logins | 8a: an agent step sees only the allowed environment and runs the repository's allowed commands; 8b: two users with their own agent logins run tasks in a shared repository, each on their own login |
| 9 | Web panel on the ui-kit, with the patterns of the infra panel's agent pages, Corivo and Hermes: 9a the API the panel needs (run trace, cost, live events, cancel, retry, continue), 9b tasks, runs and projects (any folder: a GitHub repository, a local git repository or a folder without git), 9c workflows, automations, skills, integrations, memory and accounts, 9d gates and questions in workflows, ntfy notifications | 9a: a task's agent trace, cost and turns are stored and reported, the event stream delivers changes live with a token in the header, and a continuation updates its thread's pull request; the whole stage: the daily work with agents that medialan does in the infra panel's agent pages runs in the OLIMP panel |
| 10 | medialan moves from Hermes, Jarvis and the infra panel's agent pages to OLIMP, and they are archived after the move; knowledge stays in OLIMP's database: Jarvis's areas were imported once into the memory of knowledge-area projects, one per company (`medialan`, `uniqa`, `yetiforce`) and a private one (maintainer's decision); the demo chain is a `demo` git project with its workflows, and the UI blueprints are files there; Corivo is an MCP integration that workflows use (demos, mail, database updates); deploy, the project registry, status and uptime stay in infra; decision on opening the code; remove medialan-only bits (the `status` script pointing at `../infra`, the Polish `## Weryfikacja` heading in AGENTS.md that Hermes looks up by name) | medialan's automations, workflows and knowledge run on OLIMP |
| 11 | Installation in one command: 11a the `olimp` command (`bin`) with `olimp service install`, `restart`, `status` and `logs` as a systemd user service, and the panel's update exiting for the service to start the new version (pulled ahead of stage 10, maintainer's decision, since restarts after a merge are manual today); 11b the npm package `olimp-run` (npm refuses `olimp` as too close to `jimp`), run with `npx olimp-run` and installed with the `olimp` command: compiled to JavaScript on publish (Node does not strip types under `node_modules`), the built panel inside, updates through npm; 11c `npx olimp-run server-install --platform ubuntu-vps` with a system service, HTTPS behind a reverse proxy and accounts, and a dry run with fake agents (`OLIMP_DRY_RUN=1`); a desktop app only later | 11a: after `olimp service install` OLIMP starts with WSL and `olimp service restart` restarts it; 11b: `npx olimp-run` on a clean machine with Node 24 and a logged-in `claude` starts OLIMP and a task ends with a PR; 11c: one command sets up a VPS whose panel is reached over HTTPS with sign-in |
